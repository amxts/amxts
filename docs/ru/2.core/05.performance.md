---
title: Производительность
---

Плагин компилируется в машинный код до того, как сервер его загрузит, поэтому
работа, которую он делает сам, — циклы, арифметика, массивы, текст — идёт
быстро, а с дробными числами во много раз быстрее, чем в Pawn. Время уходит
на переходы между плагином и игрой: вызов в AMX Mod X, событие по пути к
обработчику и память, которую нагруженная функция просит снова и снова. На
этой странице — цифры и привычки, которые из них следуют.

## Цифры

| Что | TypeScript | Pawn | TypeScript против Pawn |
| --- | --- | --- | --- |
| Натив: `is_user_alive(id)` | 24 / 31 нс | 11 / 11 нс | в 2–3 раза медленнее |
| Деньги игрока: `player.money`; в Pawn `get_member(id, m_iAccount)` | 67 / 82 нс | 62 / 68 нс | примерно так же |
| Здоровье игрока: `player.health`; в Pawn `get_user_health(id)` | 94 / 81 нс | 10 / 11 нс | в 7–9 раз медленнее |
| Позиция: `player.origin`; в Pawn `get_entvar(id, var_origin, origin)` | 0,8 / 1,0 мкс | 21 / 33 нс | в 30–40 раз медленнее |
| `get_member(id, m_iAccount)` из ReAPI, вызванный из TypeScript | 1,3 / 1,7 мкс | 62 / 68 нс | в 20–25 раз медленнее |
| Деньги вместе с HUD: `player.money = 800`; в Pawn `rg_add_account(id, 800, AS_SET)` | 2,5 / 3,5 мкс | 0,24 / 0,35 мкс | в 10 раз медленнее |
| Дробные числа: одно расстояние, `Math.sqrt`; в Pawn `floatsqroot` | 3,8 / 3,7 нс | 56 / 49 нс | в 13–15 раз быстрее |
| Целые числа: одно `n % d` | 62 / 74 нс | 5,9 / 4,2 нс | в 10–18 раз медленнее |
| Событие игры доходит до обработчика | 3,1 / 4,7 мкс | 75 / 87 нс | в 40–55 раз медленнее |
| Новый объект: `new Player(id)`, объектный литерал | 0,2 / 0,3 мкс | | |
| Новый `Vector`, шаблонная строка | 0,6 / 0,9 мкс | | |
| `server.players` при 5 игроках | 5,1 / 7,5 мкс | | |

Каждая цифра — время одной операции, лучшее из трёх прогонов по 100 000 —
1 000 000 операций, на сервере Windows 10 / сервере Linux в Docker на той же
машине: Intel Core i5-9400 на 2,9 ГГц, с ReHLDS, ReGameDLL и ReAPI.
Наносекунда (нс) — миллиардная доля секунды, микросекунда (мкс) —
миллионная. Событие игры — `resetMaxSpeed`, которое доставляет ReAPI, его
слушает обработчик, который ничего не делает. Плагин на Pawn работает на JIT
AMX Mod X, который при загрузке плагина превращает Pawn в машинный код.

Для масштаба: сервер делает от 100 до 1000 кадров в секунду, так что один
кадр — от 1 до 10 мс, от миллиона до десяти миллионов наносекунд.

## Чего ждать после Pawn

- **Ваш собственный код быстрый.** Цикл по своим массивам, словарям и
  объектам и арифметика с дробными числами выполняются как машинный код. В
  Pawn операция с `Float:` — вызов натива, здесь — одна инструкция.
- **`%` с целыми числами медленнее, чем в Pawn,** потому что `number` — это
  число JavaScript, внутри дробное
  ([ограничения](../1.getting-started/06.limitations.md#язык)). Это важно
  только в цикле на миллионы шагов.
- **Натив стоит в два-три раза дороже, чем в Pawn,** — десятки наносекунд.
  Несколько сотен нативов за кадр незаметны.
- **Поля фасада читаются там, где их хранит игра,** так же быстро, как
  нативы ReAPI в Pawn. Поле-вектор при каждом чтении создаёт новый `Vector`.
- **Событие доходит до обработчика на TypeScript за микросекунды,** а до
  Pawn — за десятую долю микросекунды. Событие раз в раунд, на убийство или
  на команду не заметно; событие каждый кадр для каждого игрока стоит
  посчитать.
- **Памятью управляют за вас:** то, что создала функция, освобождается,
  когда на него никто не ссылается, а стоит именно создание.

## Как писать быстрый плагин

### Сначала фасад, потом нативы

`player.money` и другие свойства игрока, оружия или сущности читают и пишут
память игры напрямую. Нативы полей ReAPI — `get_member`, `get_entvar` и
подобные — принимают хвост `...`, который вызов из TypeScript собирает на
ходу, в двадцать раз медленнее:

```ts
// так
if (player.money >= price) player.money -= price;

// не так
if (get_member(player.id, m_iAccount) >= price) set_member(player.id, m_iAccount, get_member(player.id, m_iAccount) - price);
```

Простой натив — `is_user_alive`, `user_slap` — стоит десятки наносекунд:
вызывайте его смело там, где у фасада нет своего
([нативы](../6.pawn/01.natives.md#нативы-напрямую)).

### Слушайте нужный класс

Назовите классы в параметрах обработчика, и сервер отдаст плагину только эти
события; проверка внутри обработчика выполняется, когда событие уже заплатило
за вход:

```ts
// так: игрок касается оружия на земле, и больше ничего
game.addEventListener("touch", onPickup, { toucher: "player", touched: "weaponbox" });

// не так: каждое касание каждой сущности, каждый кадр, чтобы найти те же
game.addEventListener("touch", (event) => {
	if (event.toucher.classname != "player" || event.touched.classname != "weaponbox") return;
	onPickup(event);
});
```

`classname` делает то же для события об одном классе сущностей
([один класс сущностей](02.hooks.md#один-класс-сущностей)).

### Частые события должны быть лёгкими

Некоторые события идут всё время: `"frame"` каждый кадр сервера, `preThink`
и `postThink` каждый кадр для каждого игрока, `touch`, а на каждый выстрел —
`shoot`, `traceAttack` и `primaryAttack`. На полном сервере при 1000 кадрах в
секунду `preThink` — это 32 000 вызовов в секунду, около десятой доли каждой
секунды только на то, чтобы дойти до обработчика. Делайте там лишь то, что
должно случиться в этот момент, а то, что может подождать, отдайте таймеру:

```ts
// так: десять раз в секунду, для всех сразу
setInterval(() => {
	for (const player of server.players) checkSpeed(player);
}, 100);

// не так: та же проверка в каждом кадре каждого игрока
game.addEventListener("preThink", (event) => checkSpeed(event.player));
```

### Не создавайте объекты в нагруженном цикле

Новый объект стоит пятую долю микросекунды, `Vector` или текст — больше.
Поле-вектор вроде `player.origin` при каждом чтении создаёт новый `Vector`,
как и каждое `event.player`: читайте их по одному разу.

```ts
// так: один Vector
const origin = player.origin;
const dx = origin.x - spot.x;
const dy = origin.y - spot.y;

// не так: новый Vector при каждом чтении
const dx = player.origin.x - spot.x;
const dy = player.origin.y - spot.y;
```

С текстом так же: собирайте строку HUD, когда меняется то, что она
показывает, а не при каждой отправке.

### `server.players` читайте один раз

Каждое чтение `server.players` заново спрашивает сервер и создаёт новый
список новых игроков — микросекунды при пяти игроках, больше при тридцати
двух. Прочитайте его один раз и пользуйтесь им:

```ts
// так: один список на весь цикл
const players = server.players;
for (const player of players) {
	const enemies = players.filter(other => other.team != player.team);
	warn(player, enemies);
}

// не так: новый список для каждого игрока
for (const player of server.players) {
	const enemies = server.players.filter(other => other.team != player.team);
	warn(player, enemies);
}
```

### События, а не опрос

Таймер, который спрашивает каждого игрока, не случилось ли что-то, делает
эту работу каждый раз, даже когда ничего не случилось. Событие приходит один
раз, когда это случается:

```ts
// так: игра сама говорит, когда игрок появился
game.addEventListener("spawn", (event) => giveKit(event.player), { post: true });

// не так: десять раз в секунду спрашивать каждого игрока, жив ли он уже
setInterval(() => {
	for (const player of server.players) {
		if (player.isAlive && !equipped.has(player.id)) giveKit(player);
	}
}, 100);
```

### Ждать — это `await`

Веб-запрос через [`fetch` или `useFetch`](../4.data/03.http.md) идёт рядом с
игрой: сервер продолжает работать, пока запрос ждёт, а ответ приходит в одном
из следующих кадров. Цикл, который крутится, пока что-то не изменится,
наоборот, держит весь сервер — ждите через `await`, таймер или событие
([async](04.async.md)). Файлы читаются и пишутся в собственном потоке
сервера, и промис-формы [`@amxts/core/fs`](../4.data/02.fs.md) тоже: читайте
файл один раз, при запуске плагина, а не в обработчике.

### Переход в Pawn

Вызов натива — AMX Mod X, модуля, другого плагина — стоит десятки
наносекунд, в два-три раза больше, чем платит Pawn. Натив с хвостом `...` —
`get_entvar`, `get_member`, `ExecuteForward`, форматированный текст —
собирает свои аргументы на ходу и стоит микросекунду-две. В обработчике,
который работает каждый кадр, их стоит считать; в остальных местах они не
важны.
