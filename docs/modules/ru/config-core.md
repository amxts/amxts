title: "Конфиги: config-core"
---

Файлы конфигов в INI, YAML или JSON: читаются в типизированный объект той же
формы, что его значения по умолчанию, и пишутся обратно в своём формате
вместе с комментариями. Файл, форма которого заранее неизвестна, читается
деревом значений. Плагин на TypeScript пользуется им как `configs`, без
строки импорта ([автоимпорты](../../ru/2.core/01.plugin.md#автоимпорты)). Pawn-плагины читают
INI-файлы нативами `cfg_*` из `universal_config.inc`.

## Из TypeScript

```ts
const settings = configs.load("settings", {      // configs/settings.yaml, .yml, .json, .jsonc или .ini
	chat: { prefix: "[Server]" },
	round: { time: 2.5, mode: "normal" },
	maps: ["de_dust2"],
});

settings.chat.prefix;                             // из файла или "[Server]", если в файле его нет
settings.round.time = 3;
configs.save(settings);                           // в формате файла, с комментариями
```

Значения по умолчанию задают форму объекта: у каждого поля тип его значения
по умолчанию, редактор дополняет `settings.round.time` и отвергает
`settings.round.tme`. Что есть в файле, заменяет значение по умолчанию,
значение за значением; чего в файле нет, остаётся по умолчанию.

С интерфейсом у полей появляются описания, необязательные поля и юнионы
имён:

```ts
type Mode = "normal" | "dm" | "knife";

interface Settings {
	/** Текст перед каждым сообщением в чате. */
	chat: { prefix: string };
	round: { time: number; mode: Mode };
	maps: string[];
	/** Показывается при входе; если не задан, ничего не показывается. */
	motd?: string;
}

const settings = configs.load<Settings>("settings", {
	chat: { prefix: "[Server]" },
	round: { time: 2.5, mode: "normal" },
	maps: [],
});

if (settings.motd !== undefined) print(player, settings.motd);
```

```yaml
# configs/settings.yaml
chat:
  prefix: "[Server]"
round:
  time: 2.5
  mode: normal
maps: [de_dust2, de_inferno]
motd: Welcome!
```

- Имя без расширения читает первый из `name.ini`, `name.yaml`, `name.yml`,
  `name.json` и `name.jsonc`, который есть; два из них — ошибка в консоли
  сервера, и читается первый. С расширением читается этот файл. Файла нет —
  читаются значения по умолчанию, а `save()` пишет его как `name.yaml`.
- `save(settings)` пишет каждое поле объекта в файл, из которого он
  прочитан: изменённые значения — на их местах, с комментариями, а тех, что
  в файле не было, — после них. Необязательное поле, которое не задано,
  убирается из файла.
- `load()` отдаёт копию: изменения объекта не меняют значения по умолчанию.
  Второй `load()` читает файл заново.

### Проверка того, что написано в файле

Значение, которое не подходит объекту, остаётся по умолчанию, а консоль
сервера говорит, где оно и что не так, — админ видит ошибку при старте, а не
настройку, которая молча не работает:

```
[ConfigCore] configs/settings.yaml:5:9: "time" is text ("soon"), not a number - the default stays
[ConfigCore] configs/settings.yaml:6:9: "mode" is "dmm", not one of "normal", "dm", "knife" - did you mean "dm"? - the default stays
[ConfigCore] configs/settings.yaml:2:3: unknown key "prefx" in "chat" - did you mean "prefix"?
```

- Число можно записать текстом (`"2.5"`; в INI любое значение — текст);
  логическое значение — `true`/`false`, `yes`/`no`, `on`/`off` или `1`/`0`.
- Элемент списка не того вида пропускается; одно значение там, где ждут
  список, — список из одного.
- Пустое значение (`key:` в YAML, `null` в JSON) оставляет значение по
  умолчанию. В INI `key =` — пустой текст или пустой список.
- Объект, созданный из файла, — элемент списка объектов или необязательный
  объект, которого нет в значениях по умолчанию, — получает поле, которого в
  файле нет, пустым (`""`, `0`, `false`, первое имя юниона, `[]`), и консоль
  об этом говорит.

### Что может быть в объекте

| В объекте | В файле |
| --- | --- |
| `string`, `number`, `boolean` | значение; логическое — `true`/`false`, `yes`/`no`, `on`/`off` в любом регистре или число (`0` — ложь) |
| юнион имён, `"normal" \| "dm"` | одно из них — другое называется, с ближайшим именем |
| `string[]`, `number[]`, `boolean[]`, список имён | список |
| объект, `{ prefix: string }`, любой вложенности | объект |
| список объектов, `Item[]` | список объектов |
| список списков, `string[][]` (текста, чисел, логических значений или имён) | список списков: строки значений |
| `Map<string, number>` (текста, чисел, логических значений или имён) | объект, чьи ключи — ключи map |
| `field?: T` | можно не писать: `undefined`, пока его не задаст файл или код |

::: warning
Сборка читает форму из исходника, поэтому она должна быть там написана:
значения по умолчанию — объектным литералом (и в каждом списке — значение),
или указан тип — `configs.load<Settings>(...)` или
`const defaults: Settings`. Список списков списков или объектов, юнион не из имён
(`number | string`), обобщённый интерфейс и интерфейс с `extends`
отвергаются с местом и тем, как исправить. Объект из
`configs.load(name, { ... })` без типа передаётся в функцию как
`typeof settings` или как интерфейс с теми же полями.
:::

### INI-файлы

INI-файл — это секции значений: `[chat]` с `prefix = [Server]` — это
`chat.prefix`.

```ini
; configs/settings.ini
[chat]
prefix = [Server]

[round]
time = 2.5
mode = normal
modes = normal dm
```

- Каждый объект на верхнем уровне объекта — секция; его поля — ключи
  секции.
- Список — строка значений (`modes = normal dm`); объект внутри секции —
  блок `key = { ... }`; логическое значение пишется `1` или `0`.
- Список списков — блок строк в кавычках: `CVARS = { "mp_timelimit" "30" }`
  — это `[["mp_timelimit", "30"]]`. При сохранении он остаётся блоком — и
  строки из одного значения тоже — с комментариями над его строками.
- `Map` на верхнем уровне — своя секция: `[prices]` с `de_dust2 = 3`.

::: warning В INI-файле
- **Ключи ищутся без учёта регистра, имена секций — нет:** `PREFIX = ...` —
  это `prefix`, а `[CHAT]` — не `chat`, и консоль об этом скажет.
- **Текст с пробелами берётся в кавычки:** `title = "Main menu"`. Без кавычек
  это список слов: текстовое поле остаётся со значением по умолчанию, а
  консоль говорит почему, и нативы `cfg_*` Pawn и menu-core читают первое
  слово.
- **Нет места значению на верхнем уровне объекта, которое не объект, и
  спискам объектов.** Такое поле в INI-файле остаётся по умолчанию, и консоль
  один раз об этом говорит. Такой конфиг пишите в YAML или JSON.
:::

### Форматы

- **YAML:** отображения и списки — с отступами или в `{ }` и `[ ]`; простой
  текст и текст в кавычках с экранированиями; блоки `|` и `>`; числа,
  `true`/`false` и `null`, как их читает YAML 1.2 (`yes` — текст);
  комментарии `#`; `---` и `...` вокруг документа.
- **JSON:** как пишется JSON, плюс комментарии `//` и `/* */` и запятая после
  последнего поля или элемента (JSONC), и в файлах `.json` тоже.
- **INI:** `[секция]` — объект; строка из нескольких значений — список; блок —
  объект или список строк. Ключи в секции ищутся без учёта регистра.
- Сохранение оставляет комментарии на отдельных строках, пустые строки и
  отступы JSON; комментарий после значения на той же строке пропадает.

::: warning
Якоря и ссылки YAML (`&`, `*`), теги (`!`), сложные ключи (`?`), директивы и
несколько документов в одном файле не читаются. Файл с ними — как и с любой
ошибкой — читается пустым объектом, а консоль сервера говорит, где:
`configs/settings.yaml:4:9: anchors and aliases (& and *) are not supported - write the value out`.
Весь список и то, что сохраняется при записи, — в
[Ограничениях](../../ru/1.getting-started/06.limitations.md#конфиги).
:::

### Файлы неизвестной формы

Файл, ключи которого заранее неизвестны, — список карт со своими
настройками, файл, который пишет другой плагин, — читается деревом значений:

```ts
const maps = configs.read("maps");                // configs/maps.yaml, .json или .ini

for (const map of maps.values()) {
	console.log(`${map.key}: ${map.getNumber("rounds", 30)} rounds`);
}

maps.setNumber("de_dust2.rounds", 20);
maps.save();
```

- Значение — это `ConfigNode`: `kind` (`"object"`, `"array"`, `"string"`,
  `"number"`, `"boolean"`, `"null"`), `key` и `file`, `line`, `column` — где
  оно прочитано. `get(path)`, `keys(path)` и `values(path)` ведут внутрь;
  путь — `chat.prefix` или `items[0].name`: элемент списка — `[0]`, а
  `items.0.name` ищет ключ `0`.
- `getString`, `getNumber`, `getBoolean` и `getStrings` принимают запасное
  значение на случай, если значения нет или оно другого вида; `set`,
  `setNumber`, `setBoolean` и `setStrings` создают объекты на пути (и списки
  перед элементом `[0]`) и
  возвращают false, если путь идёт через текст или число. `parse(text,
  format)` так же читает текст.

Базовую папку может задать и проект, в `amxts.config.ts`:

```ts
export default defineConfig({
	modules: ["@amxts/config-core"],
	configs: { baseDir: "myplugin" },    // configs/myplugin/
});
```

## Из любого плагина: один config-core на сервер

На сервере один экземпляр `@amxts/config-core` — плагина
config-core. Любой другой плагин, который им пользуется, вызывает этот
экземпляр, с теми же функциями и типами (см.
[Общие модули](../../ru/5.modules/01.shared-modules.md)): папка конфигов одна на весь сервер
(menu-core читает из неё и свои меню). `ConfigNode` — объект владельца:
каждый его метод выполняется у владельца, так что чтение
файла значение за значением из другого плагина — вызов на значение: при
старте это нормально, в каждом кадре лучше не надо. Объект, который отдаёт
`configs.load()`, — собственный объект плагина: `load()` и `save()` читают
и пишут файл через владельца, а между ними `settings.round.time` — такое же
поле, как любое другое.

## Для Pawn-плагинов

Проект, плагины которого на TypeScript config-core не пользуются, оставляет
его для своих Pawn-плагинов через `pawn: ["@amxts/config-core"]` в
`amxts.config.ts`: иначе модуль, которым не пользуется ни один плагин, в
сборку не попадает ([собирается только то, чем
пользуются](../../ru/2.core/01.plugin.md#собирается-только-то-чем-пользуются)).

Плагин config-core отдаёт Pawn-плагинам 28 нативов из
`universal_config.inc` — `cfg_load_file`, `cfg_get_value`, `cfg_set_int` и
остальные — с их сигнатурами, так что собранные `.amxx` работают с ним без
изменений. Pawn-плагины пишут `#include <universal_config>`.

Отдавать эти нативы на сервере может только один плагин: если в `plugins.ini`
есть другой Pawn-плагин с нативами `cfg_*`, закомментируйте его.

## Как работают нативы

Ограничений Pawn нет: ключ и значение любой длины, секция хранит все записи,
блоки вкладываются на любую глубину, файлов загружается сколько угодно. Число
читается так, как его читает `parseFloat` (`1e5` — 100000), и пишется как
есть (`2.5`, а не `2.500000`). `CFG_CONTENT_SIMPLE` и `CFG_CONTENT_STRINGS` —
одно содержимое: блок любого из них хранит строку значений.
