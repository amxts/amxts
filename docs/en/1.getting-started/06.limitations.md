title: Limitations
---

What a plugin can run into, in one place, each with what to write instead.
The build, the editor or the server console says so for almost every item
below; this page is where to look up what it means.

## The language

A plugin is TypeScript compiled to WebAssembly and then to machine code.
What TypeScript has and a plugin does not:

- **`throw` takes an `Error` or a string,** which becomes an `Error` with it
  as the message: `throw 42` does not build. A `catch` gets an `Error` -
  `error.message`, `error.name`, `instanceof` for a class of your own. A
  crash that is not an error - a stack overflow - ends the call past every
  `catch`.
- **No unions of different types.** `number | string`, and
  `cond ? 1 : "a"`, do not build. Unions of string literals
  (`"CT" | "TERRORIST"`), `T | null` and `T | undefined` work, and so do
  `true | false | "default"` and a function-or-list option such as
  menu-core's `enabled`. Use two parameters, two functions, or a common base
  class.
- **No `any` and `unknown`.** Every value has a type when the plugin is
  built.
- **An object literal takes its type from its values,** so each value needs
  one: `{ owner: null }` or `{ items: [] }` alone does not build - declare an
  interface (`const team: Team = { ... }`), or write the literal where the
  type is known.
- **A plain object goes where another is expected when it has the same
  fields:** `{ y: 2, x: 1 }` is a `Point` of `x` and `y`, and a `label`
  given goes where `label?` is optional; one that leaves an optional field
  out does not - write the literal where the type is known.
- **An interface with a method or an accessor is implemented by a class:**
  an object literal of it does not build. An interface of fields - one that
  extends another such interface too - is the type of a plain object.
- **A class goes where an interface of fields is expected when it says
  `implements`,** and extends no other class: `class Spot implements Point`
  is a `Point`; a class of the same fields without `implements` is not.
- **`JSON.parse` is told what it reads:** `JSON.parse<Settings>(text)`, or
  `JSON.parse(text) as Settings`; alone it does not build. A field the text
  leaves out that is neither optional nor has a default is a `TypeError`,
  where JavaScript leaves it `undefined`. `JSON.stringify` takes no replacer
  function ([JSON](../4.data/02.fs.md#json)).
- **Regular expressions have no lookbehind** (`(?<=...)`), named groups,
  `\p{...}` or the `u` and `d` flags: such a pattern is a `SyntaxError`. A
  group that did not match reads as `""`, not `undefined`; a function given to
  `replace` gets the match and up to four groups. A match that takes more
  than five million steps throws an `Error`, so that a pattern that
  backtracks without end does not hold the server.
- **A date knows a few languages and no `Intl`:** `toLocaleString` and the
  rest take a language (`en-US`, `en-GB`, `de`, `fr`, `ru`), not options, and
  `toString` writes the time zone as its offset, without its name in
  brackets ([time](../2.core/01.plugin.md#time-and-randomness)).
- **Syntax that does not build:**

  | Does not build | Write instead |
  | --- | --- |
  | `function*`, `yield` | an array, or `async` functions and `await` |

- **A class field holding an arrow that returns more than a plain value
  needs its type:** `onTick = () => { ... }` and `double = (n: number) => n * 2`
  build; `label = () => this.makeLabel()` needs
  `label: () => string = () => this.makeLabel()`.

## Variables and optional values

- **A method that runs early through a base class** may read a variable
  before its declaration as an empty value, where JavaScript throws a
  `ReferenceError`.
- **Inside a closure, a boolean left out is `false`:** a `flag?: boolean`
  parameter, or a variable that holds an optional boolean field, read in an
  arrow function made inside the function does not see it was left out -
  `() => flag ?? true` is `false`. Read it outside: `const loud = flag ?? true`.
- **`undefined` is known by the type written where it is read:** an
  optional field or parameter, a variable or a function's result of
  `T | undefined`, `find` and `map.get` - and a variable that holds one of
  them - print as `undefined` and count as `NaN`. An item read by index from
  an array of `T | undefined` prints text as `null`, and a number counted
  with stays `undefined`: give it a default with `??` first.
- **`x!` on a `null` throws a `TypeError` right there,** where TypeScript's
  `!` does nothing and JavaScript throws only where the value is used.

## Async and promises

- **Async generators** (`async function*`) do not build.
- **A list in a variable given to `Promise.all` holds promises:**
  `Promise.all([load(), 5])` takes a plain value, `Promise.all(numbers)` of a
  `number[]` does not build.
- **`Promise.race` and `any` need one type:** promises of a `number` and a
  `string`, or a `number` and a `sleep`, do not build. Await them one by one.
- **`Promise.all` of different types takes up to 8 promises;** promises of
  one type, or a list, have no such limit ([async](../2.core/04.async.md)).
- **A game listener answers only before its first `await`**
  ([game events](../2.core/02.hooks.md#async-listeners)).
- **A waiting async function keeps up to 4 KB of its own state;** one that
  needs more is stopped, with a message in the console.

## Events, commands, forwards, timers

- **An event name is written out:** `server.addEventListener(name, ...)`
  with the name in a variable does not build - the name picks the event's
  type. So is a `"playerchange"` listener's field: `{ field: "ghost" }`, not a
  variable. Without `field`, the event's `value` has no type: read the field
  from `event.player`.
- **A game listener either always answers or never does.** One that should
  answer only sometimes returns nothing and calls `event.preventDefault()`,
  or always answers, repeating the game's rule for the rest
  ([game events](../2.core/02.hooks.md)).
- **Vector fields of game events are read-only** (`traceAttack`'s `dir`,
  `fireBullets`'s positions): stop the event and act yourself.
- **Two fields of game events are numbers:** `pain`'s `lastHitGroup`;
  `hasRestrictItem`'s `item` reads as a `Weapon` but holds the item's number
  - use `event.item.id`.
- **An event of one class of entity needs `classname`** (`primaryAttack`,
  `deploy`, `think`, `use`): without it the listener is not added, with a line
  in the console. On an event Ham Sandwich delivers,
  `stopImmediatePropagation()` blocks the game's function but not other
  plugins' listeners ([game events](../2.core/02.hooks.md#one-class-of-entity)).
- **A message's arguments are read one kind at a time:** `event.args.number(i)`
  or `event.args.text(i)` (`isText(i)` says which), not an array of numbers
  and texts together - a value of either type has nowhere to be stored. The
  common messages have typed fields ([Plugin](../2.core/01.plugin.md#messages-to-clients)).
- **A native that takes a callback by its public's name** - `register_think`,
  `set_native_filter` - gets one from `publicFor(handler, key)`.
- **A native of your own takes up to 64 arguments** as Pawn passes them - an
  array or a string result counts twice, with its size; more stops the build
  ([natives](../6.pawn/01.natives.md#the-rules)).
- **A forward takes up to 32 arguments,** as many as AMX Mod X gives a
  forward. A `Team` or a `RoundWinner` argument needs the forward declared in
  an include. A forward a Pawn plugin raises reaches TypeScript only when an
  include amxts comes with declares it, and an array among its arguments
  arrives whole only when the include gives the array's size
  (`Float:origin[3]`); an array without one arrives empty
  ([forwards](../2.core/03.forwards.md)).
- **In `"connect"`, `"authorized"` and `"putinserver"` the player is a
  `Client`:** no health or weapons yet ([plugin](../2.core/01.plugin.md#server-events)).
- **A timer waits at least 0.1 second** and fires on a server frame, as every
  AMX Mod X timer does.
- **Precaching is possible only while the map loads:** `server.precache` at
  the top level of a file, or in the `"precache"` event. A plugin reloaded in
  the middle of a map gets no `"precache"` event; its top level finds a file
  the map already precached, and a file no plugin precached then waits for
  the next map. A model the game is given without being precached stops the
  server ([plugin](../2.core/01.plugin.md#sounds-and-precaching)).

## Chat and menu colours

- **One team colour per chat message.** Red, blue, grey and `!t` share it:
  the first one in the line wins, and the others show in it.
- **Each place draws its own tags.** `!w` (white) and `!R` (to the right
  edge) are for menus; `!g`, `!b` and `!t` for chat. A tag a place does not
  draw is removed from the text, and nothing warns.
- **`"center"`, `"console"` and `"notify"` have no colours:** the text shows
  as written, tags included.
- **Tags are case-sensitive:** `!R` is not red ([colours](../2.core/01.plugin.md#colours)).
- **`lang.translate` takes its arguments as strings:** a number goes in as
  text, `` `${seconds}` `` ([translations](../2.core/01.plugin.md#translations)). A
  dictionary line is read up to 511 bytes.

## Menus

- **menu-core has been tried in game only a few times;** its behaviour may
  still change.
- **In code a requirement is a function:** `enabled` and `visible` take a
  test, not a name registered for menu files (`IS_ALIVE`, `FLAG_d`) - write
  `(player) => player.isAlive`.
- **`%name%` placeholders are for menu files and Pawn plugins.** In code the
  text is a function: `` (player) => `Heal (${player.health} HP)` ``.
- **`NAME:param` in a menu file takes the rest of the line,** spaces and
  all: write it after the other names of a `visible`, `enabled` or `when`.
- **An INI menu cannot hide an item:** its condition column greys the item
  out; `visible` is YAML's and JSON's ([menus](../../modules/en/menu-core.md#inis-columns)).
- **A YAML or JSON item's name is not split on `|`:** its faces are written
  with `variants`.
- **A flag of an INI menu is `YES` or `NO`:** `true`, `1` or `yes` is warned
  of, with the word to write, and is `NO`.
- **Text with spaces in an INI menu is quoted:** `TITLE = "Main menu"`;
  unquoted, only the first word is read.
- **A colour in a menu file is a tag,** `!y`: Pawn's codes (`\y`, `\r`) are
  warned of and left out. Text from Pawn - a Pawn plugin's items, a lang
  dictionary - keeps its codes.
- **The placeholders are `%time%` and `%target%`:** `%TIME%` and `%s` are
  left as written.
- **`ADMIN` and `ACCESS_ADMIN` are not built in:** a plugin registers them,
  or write `IS_ADMIN` (any admin) or `FLAG_<letters>` (`FLAG_d`)
  ([menus](../../modules/en/menu-core.md#the-fields)).

## Players and entities

- **Entity properties need reapi, and so do the game events it delivers.**
  Without it, the
  player's basics, the player actions (`give`, `respawn`, …) and
  `Entity.find`/`findAll`/`create` still work ([players](../3.game/02.players.md)).
- **A value no name stands for** - another plugin or a mod wrote it - reads
  as `"unknown"`, and assigning `"unknown"` changes nothing. Read the number
  with the native: `get_entvar(player.id, var_rendermode)`.
- **Plain numbers:** `activity` and `idealActivity` (the model's `ACT_*`),
  `autoWepSwitch`, `inSpecialReload`.
- **No property for:** array members (`m_rgAmmo`, …; the weapons are
  `player.items`), `var_controller`, `var_blending`. Use `get_member` and `set_member`
  ([entities](../3.game/01.entities.md#fields-that-are-not-properties)).
- **A vector or a text field read through a native needs its type:**
  `get_entvar<Vector>(id, var_origin)`, `get_member<string>(id, m_szAnimExtention)`.
  Without it the field reads as a number, and a vector or text field reads
  as `0`, with a line in the console that says what to write.
- **`player.health` is a whole number;** another entity's `health` is a
  fraction.
- **A flag list writes back through `push` only:** `pop` and `splice` change
  the array, not the game. To remove a flag, assign a filtered array.
- **Shared player fields** are `boolean`, `number`, `string`, a union of
  string literals, `Player[]` or an object of those; never optional, and an
  object's members are not objects. A name `Player` already has is refused.

## Effects and precaching

- **No effect for decals** (a bullet hole, a spray - they need a decal's
  index), for the engine's tracer colours or for a text message
  (`player.showHud` is that); send them with `message_begin` and `write_*`
  ([effects](../3.game/03.effects.md)).
- **Some sizes are the effect's own numbers,** `0` to `255`: a beam's `width`
  and `noise`, a sprite's `scale`; each option's description says what one
  step is.
- **A file is precached only while the map loads.** Asked for later, a file
  no plugin precached is a line in the console, and an effect that draws it
  is not sent.

## Natives and storage

- **A plugin's own natives** are its file's `export function`s, with the
  parameter types [natives](../6.pawn/01.natives.md) lists; another type stops the build.
- **After `amxts_reload`,** a native the reload added is there only for Pawn
  plugins that load later.
- **Text is cut by AMX Mod X and the game, not on the way:** a native gets
  a string whole, up to the 16383 bytes AMX Mod X reads, and writes at most
  16384 cells into a buffer, however long it is. A native with a
  `const fmt[], any:...` tail (`client_print`, `server_print`, `format`, …)
  formats a line of at most 4095 bytes, and `server_print` prints 254 of
  them. The game shows about 190 bytes of a chat line - about 95 Cyrillic
  letters - and 126 of a console line sent with `client_print`.
- **A buffer's length is never negative:** a native given a buffer and a
  length below 0 - the `-1` that `ArrayGetArray`, `ArrayPushArray` and other
  `cellarray` natives read as "the whole item" - is not called and answers
  `0`. Pass the buffer's own length.
- **`Storage` holds text:** `value.toString()` in, `parseInt(value)` out. It
  reaches the disk when the map changes or the server stops cleanly; a crash
  loses what was set since the last map change. A value reads back up to 255
  bytes of UTF-8 - about 127 Cyrillic letters.

## Configs

### Typed configs - `configs.load`

- **The object of `configs.load(name, { ... })` without a type has no type
  name,** so no function can take it as a parameter: declare an interface and
  write `configs.load<Settings>(name, defaults)`.
- **The build reads the shape from the source,** and refuses, with the place
  and the fix: an empty list without a type, a defaults variable without a
  declared type, a list of lists of lists or of objects, a `Map` of lists or
  objects, a union that is not of names (`number | string`), a generic
  interface or one that `extends` another, a field named with a string, a
  type that contains itself.
- **A `Map`'s keys have no `.` and no `[`:** such a key cannot be read or
  written.
- **INI has no place for a top-level value that is not an object, or for a
  list of objects:** such a field keeps its default, and the console says so
  once. Write that config in YAML or JSON.
- **In INI, section names are case-sensitive and keys are not:** `[CHAT]` is
  not `chat`.
- **Saving** writes a YAML list written `[a, b]` one item per line, and drops
  a comment after a value on its line and comments inside `{ }` and `[ ]`.
  Comments on lines of their own and blank lines are kept.

### Config files

- **One name, one file.** `configs.load("settings")` reads the first of
  `settings.ini`, `.yaml`, `.yml`, `.json`, `.jsonc`; two of them are an error
  in the console, and the first is read.
- **YAML is the part configs use.** Not read: anchors and aliases (`&`, `*`),
  tags (`!`), complex keys (`?`), directives, several documents, a plain value
  that goes on for several lines (quote it, or use `|` or `>`), tabs in
  indentation, a key written twice, a key inside `[ ]`. Each is an error with
  the file, line and column, and the file reads as empty.
- **`yes` and `no` are text in YAML.** A typed config takes them for a
  boolean; a menu file wants `true` and `false`.
- **An INI value with spaces is quoted:** `title = "Main menu"`. Unquoted, it
  is a list of words: Pawn's `cfg_*` natives and menu-core read the first
  word, and a typed config keeps its default and says why.
- **An item of a list is `[0]` in a path:** `items[0].name`; `items.0.name`
  looks for a key `0`.

## Shared modules

The details are on [shared modules](../5.modules/01.shared-modules.md).

- **What cannot cross between plugins does not build:** a `Map`, a `Set`, a
  `Record` with keys of any string, a generic class, a class from the standard library, a type the module does
  not export, a computed default, a generic or `async` function, a rest
  parameter, an exported variable (`export let count`) - an object of a
  class of the module's own (`export const counter = new Counter()`) does
  cross.
- **An array or object field of a shared object reads as a copy:** `push` on
  it changes the copy. Use the module's method, or assign the whole field.
- **Every call copies its arguments both ways:** fine at start-up, costly
  every frame.
- **The module's plugin and its callers are built from the same module
  source;** a plugin built against another version gets a line in the console
  instead of the call.

## Modules and the `amxts` command

- **Not on npm yet.** `npm create amxts` and installing from npm work once
  the packages are published; until then create a project with `--local`
  ([getting started](02.quick-start.md#a-project)).
- **A module's code imports what it uses.** Auto-imports reach a project's
  plugins; a module package's files and a file under the plugins folder's
  `modules/` are built in projects and on servers whose settings they do not
  know, so they name their imports.
- **A module gives one name**: itself as a namespace (`imports: [{ from, as }]`)
  or one of its exports (`imports: [{ from, name }]`) - not a list of its
  functions or types; `menus.Menu` is a type of the namespace.
- **A module whose natives only Pawn plugins call is left out of the build**
  unless `pawn` in `amxts.config.ts` names it: the build does not read Pawn
  plugins.
- **A module's `meta`, `requires`, `defaults` and `imports` are literals:** the build
  reads them without running the module. Besides `setup`, `defineModule` has
  no lifecycle hooks: listen to server events inside `setup`.
- **Tests run with `amxts test`,** which is `bun test`; other test runners
  are not supported.
- **A native the fake server does not answer stops the test** with its name;
  answer it with `server.defineNative(name, native)` in the test, or in a
  module's [test kit](../7.testing/01.index.md#a-modules-test-kit).

## The editor

- **TypeScript 5.9, 6 and 7** work in the editor. The build and
  `amxts typecheck` use the TypeScript 5 the core installs.
- **A field the editor accepts may be missing in the build:** the editor
  sees the fields every file of the plugins folder adds to `Player`, the
  build only those of the files the plugin imports. Add the `import` of the
  file that declares it.
- **knip calls the core and modules unused** in a project created with
  `--local`, where they are linked.
- **Live help in menu files is for VS Code only,** through the amxts
  extension ([menus](../../modules/en/menu-core.md#editor-support)).
- **The extension knows the names written as a string in the workspace.**
  A name in a variable (`menus.addAction(name, ...)`), or one only a Pawn
  plugin on the server registers, is a warning in the editor; the server's
  check on its first frame is the one that counts.

## The server

- **A plugin is built for its server's system.** A `.aot` is machine code
  for Windows or for Linux, and one built for the other does not load: the
  console says `was compiled for a Linux server, and this one runs Windows`
  (or the other way). The build reads the system off `AMXTS_SERVER`; for a
  server it cannot see, set `AMXTS_SERVER_OS` or pass `--os`
  ([the server's system](03.cli.md#the-servers-system)). A `.ts` the server
  compiles itself is always right.
- **A `.ts` the server compiles holds the server** for the second or two the
  compile takes: in the middle of a round the game freezes. On a server
  people play on, deploy `.aot` files built in a project
  ([installing on a server](04.install.md#written-on-the-server)).
- **ReHLDS is recommended; plain HLDS has not been tried.** Without reapi
  there are no entity properties and none of the game events it delivers.
- **AMX Mod X 1.9 or later.**
