---
title: Performance
---

A plugin is compiled to machine code before the server loads it, so the
work it does on its own - loops, arithmetic, arrays, text - is fast, and with
fractions many times faster than Pawn's. What costs time is crossing between
the plugin and the game: a call into AMX Mod X, an event on its way to a
listener, and memory a busy function asks for again and again. This page
gives the numbers and the habits that follow from them.

## The numbers

| What | TypeScript | Pawn | TypeScript against Pawn |
| --- | --- | --- | --- |
| A native: `is_user_alive(id)` | 24 / 31 ns | 11 / 11 ns | 2-3 times slower |
| A player's money: `player.money`; Pawn `get_member(id, m_iAccount)` | 67 / 82 ns | 62 / 68 ns | about the same |
| A player's health: `player.health`; Pawn `get_user_health(id)` | 94 / 81 ns | 10 / 11 ns | 7-9 times slower |
| A position: `player.origin`; Pawn `get_entvar(id, var_origin, origin)` | 0.8 / 1.0 µs | 21 / 33 ns | 30-40 times slower |
| ReAPI's `get_member(id, m_iAccount)` called from TypeScript | 1.3 / 1.7 µs | 62 / 68 ns | 20-25 times slower |
| Money with its HUD: `player.money = 800`; Pawn `rg_add_account(id, 800, AS_SET)` | 2.5 / 3.5 µs | 0.24 / 0.35 µs | 10 times slower |
| Fractions: one distance, `Math.sqrt`; Pawn `floatsqroot` | 3.8 / 3.7 ns | 56 / 49 ns | 13-15 times faster |
| Whole numbers: one `n % d` | 62 / 74 ns | 5.9 / 4.2 ns | 10-18 times slower |
| A game event reaching a listener | 3.1 / 4.7 µs | 75 / 87 ns | 40-55 times slower |
| A new object: `new Player(id)`, an object literal | 0.2 / 0.3 µs | | |
| A new `Vector`, a template string | 0.6 / 0.9 µs | | |
| `server.players` with 5 players | 5.1 / 7.5 µs | | |

Each figure is the time of one operation, the best of three runs of 100 000
to 1 000 000, on a Windows 10 server / a Linux server in Docker on the same
machine: an Intel Core i5-9400 at 2.9 GHz, with ReHLDS, ReGameDLL and
ReAPI. A nanosecond (ns) is a billionth of a second, a microsecond (µs) a
millionth. The game event is `resetMaxSpeed`, which ReAPI delivers, heard by
a listener that does nothing. The Pawn plugin runs on AMX Mod X's JIT, which
turns Pawn into machine code as the plugin loads.

For scale: a server runs 100 to 1000 frames a second, so one frame is 1 to
10 ms - a million to ten million nanoseconds.

## What to expect coming from Pawn

- **Your own code is fast.** A loop over your arrays, maps and objects, and
  arithmetic with fractions, run as machine code. In Pawn a `Float:`
  operation is a native call; here it is one instruction.
- **`%` on whole numbers is slower than Pawn's,** because a `number` is a
  JavaScript number, a fraction underneath
  ([limitations](../1.getting-started/06.limitations.md#the-language)). It
  matters only in a loop of millions.
- **A native costs two or three times what it costs Pawn** - tens of
  nanoseconds. A few hundred natives a frame go unnoticed.
- **The facade's fields are read where the game keeps them,** as fast as
  ReAPI's natives in Pawn. A field that is a vector makes a new `Vector`
  each time it is read.
- **An event costs microseconds to reach a TypeScript listener,** where it
  costs Pawn a tenth of one. An event a round, a kill or a command does not
  register; one every frame for every player is worth counting.
- **Memory is managed for you:** what a function makes is freed when nothing
  holds it, and making it is what costs.

## Writing a fast plugin

### The facade before the natives

`player.money` and the other properties of a player, a weapon or an entity
read and write the game's memory directly. ReAPI's field natives -
`get_member`, `get_entvar` and their like - take a `...` tail, which a
TypeScript call builds as it runs, twenty times slower:

```ts
// so
if (player.money >= price) player.money -= price;

// not so
if (get_member(player.id, m_iAccount) >= price) set_member(player.id, m_iAccount, get_member(player.id, m_iAccount) - price);
```

A plain native - `is_user_alive`, `user_slap` - costs tens of nanoseconds:
call it freely where the facade has nothing of its own
([natives](../6.pawn/01.natives.md#calling-natives-directly)).

### Listen to the class you need

Name the classes in the listener's options, and the server hands the plugin
only those events; a check inside the listener runs after the event has
already paid its way in:

```ts
// so: a player touching a weapon on the ground, nothing else
game.addEventListener("touch", onPickup, { toucher: "player", touched: "weaponbox" });

// not so: every touch of every entity, every frame, to find the same ones
game.addEventListener("touch", (event) => {
	if (event.toucher.classname != "player" || event.touched.classname != "weaponbox") return;
	onPickup(event);
});
```

`classname` does the same for an event about one class of entity
([one class of entity](02.hooks.md#one-class-of-entity)).

### Keep frequent events light

Some events come all the time: `"frame"` every server frame, `preThink` and
`postThink` every frame for every player, `touch`, and on every shot
`shoot`, `traceAttack` and `primaryAttack`. On a full server at 1000 frames
a second, `preThink` is 32 000 calls a second - about a tenth of every
second just reaching the listener. Do there only what must happen at that
moment, and let a timer do what can wait:

```ts
// so: ten times a second, for everyone at once
setInterval(() => {
	for (const player of server.players) checkSpeed(player);
}, 100);

// not so: the same check on every frame of every player
game.addEventListener("preThink", (event) => checkSpeed(event.player));
```

### Do not make objects in a busy loop

A new object costs a fifth of a microsecond, a `Vector` or a text more. A
vector field such as `player.origin` makes a new `Vector` on every read, and
so does every `event.player`: read each once.

```ts
// so: one Vector
const origin = player.origin;
const dx = origin.x - spot.x;
const dy = origin.y - spot.y;

// not so: a new Vector on every read
const dx = player.origin.x - spot.x;
const dy = player.origin.y - spot.y;
```

Text works the same way: build a HUD line when what it shows changes, not
every time it is sent.

### Read `server.players` once

Every read of `server.players` asks the server again and makes a new list of
new players - microseconds with five players, more with thirty-two. Read it
once, and reuse it:

```ts
// so: one list for the whole loop
const players = server.players;
for (const player of players) {
	const enemies = players.filter(other => other.team != player.team);
	warn(player, enemies);
}

// not so: a new list for every player
for (const player of server.players) {
	const enemies = server.players.filter(other => other.team != player.team);
	warn(player, enemies);
}
```

### Events, not polling

A timer that asks every player whether something has happened does that
work every time, also when nothing has. An event arrives once, when it
happens:

```ts
// so: the game says when a player has spawned
game.addEventListener("spawn", (event) => giveKit(event.player), { post: true });

// not so: asking every player, ten times a second, whether he is alive yet
setInterval(() => {
	for (const player of server.players) {
		if (player.isAlive && !equipped.has(player.id)) giveKit(player);
	}
}, 100);
```

### Waiting is `await`

A web request with [`fetch` or `useFetch`](../4.data/03.http.md) runs beside
the game: the server goes on while it waits, and the answer comes in a later
frame. A loop that spins until something changes holds the whole server
instead - wait with `await`, a timer or an event
([async](04.async.md)). Files are read and written on the server's own
thread, the promise forms of [`@amxts/core/fs`](../4.data/02.fs.md) too:
read a file once, when the plugin starts, rather than in a listener.

### Crossing into Pawn

A call to a native - AMX Mod X's, a module's, another plugin's - costs tens
of nanoseconds, two or three times what Pawn pays. A native with a `...`
tail - `get_entvar`, `get_member`, `ExecuteForward`, formatted text - has
its arguments put together as it runs and costs a microsecond or two. In a
listener that runs every frame, count those; anywhere else, they do not
matter.
